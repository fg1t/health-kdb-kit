# KDB — Health-Research Vault Schema & Conventions

This is a personal knowledge base: a typed markdown wiki maintained by the
`kdb-librarian` skill, browsed in Obsidian, and readable by any Claude session.
This file is the schema — the contract every page and every librarian operation
follows. It is this vault's *only* copy of the contract (there is no separate
stock file to fall back on), so it is written to be self-contained.

## 1. What this vault is

A health-research library — studies, extracted claims, interventions, conditions,
and topics — kept so that its owner and an assistant working alongside her can
design health products/services on evidence that has been read, graded, and
checked for who it actually applies to, rather than re-litigated from scratch
every time.

Two kinds of writer share it: the owner, who hand-authors her own personal
health pages directly, and the assistant, which contributes research through
the inbox → librarian pipeline (see §6). Nothing in this file is specific to
any one assistant's name or identity — an assistant working in this vault is
referred to generically throughout.

Pages may be written in English, in 中文, or mixed within a single page.
**Never language-normalize a page** — do not translate, retranslate, or
rewrite a page's language mix as part of a lint, ingest, or any other
operation. The language a page was written in is part of its content.

## 2. Layout

| Folder | `type` | Contents |
|---|---|---|
| `concepts/` | `Concept` | Ideas, mental models, technologies |
| `people/` | `Person` | People |
| `companies/` | `Company` | Companies, funds, institutions |
| `sources/` | `Source` | One page per ingested source; original content preserved |
| `playbooks/` | `Playbook` | Procedures, how-tos, checklists |
| `notes/` | `Note` | Catch-all until a real type emerges |
| `studies/` | `Study` | One page per research study — design, N, population, findings |
| `claims/` | `Claim` | Graded, falsifiable statements extracted from studies |
| `interventions/` | `Intervention` | Things you can do (diet, supplement, protocol) — evidence by population |
| `conditions/` | `Condition` | Health conditions the library tracks evidence against |
| `topics/` | `Topic` | Cross-cutting subject pages linking claims and interventions |
| `attachments/` | — | PDFs, images (referenced via `![[file.pdf]]`) |
| `inbox/` | — | Unprocessed drops; emptied by ingest |
| `.scripts/` | — | Maintenance scripts (`regen-index.py`, `lint.py`) |
| `.kdb/types.json` | — | Registers the five health folders above with `lint.py`/`regen-index.py` |
| `templates/` | — | Skeleton pages for the five health types (not linted; copy, don't link) |

Reserved files (no frontmatter): `CLAUDE.md` (this schema), `index.md`
(regenerated by `.scripts/regen-index.py` — never hand-edit), `log.md`
(append-only ops log, newest first), `LICENSE`, and an optional `README.md`.

New type folder rule: create only when ~3+ pages would use it; add the row to
the table above in the same commit. This table is the type registry (mirrored
mechanically for the health types in `.kdb/types.json`, which the scripts read).

## 3. Page format

Every page carries YAML frontmatter. The base fields apply to every page in
every folder, health types included:

```yaml
---
type: Concept            # required, from the table above
title: Economic Moat
description: One-sentence summary — used by index regeneration and agent scans
tags: [investing]        # domain lives in tags, not folders
created: 2026-07-06
updated: 2026-07-06
source: https://...      # Source pages only: the original URL
---
```

- Filenames: kebab-case, e.g. `concepts/economic-moat.md`.
- Body: structured markdown — headings, lists, tables over prose. Relationships
  are `[[wikilinks]]`; the *kind* of relationship is stated in surrounding
  prose (e.g. "coined by [[li-lu]]").
- **Knowledge lives in entity pages, not source pages.** A Source page
  preserves the original material (the immutable raw layer). Every ingest must
  ALSO synthesize into the entity pages it touches — a source that is filed
  but never synthesized is an "orphan source" (lint violation). The same
  raw-vs-derived split holds inside the health types: a `studies/` page is the
  immutable raw record of what a study found; a `claims/` page is a derived,
  graded synthesis that cites it; an `interventions/`/`conditions/`/`topics/`
  page is a further derived rollup that cites claims. Never fold derived
  judgment into a raw study page — add a claim or a topic note instead.
- Pages state current best understanding. When new information supersedes a
  claim, update the claim in place and leave a one-line
  `> superseded: <old claim> (YYYY-MM-DD)` note beneath it. Git history and
  `log.md` are the audit trail. No confidence scores beyond the evidence
  grade below, no decay.

### Health frontmatter reference

The five health types carry the base fields above (`type`, `title`,
`description`, `tags`, `created`, `updated`) plus these type-specific fields.
Field names are exact — templates in `templates/` and the librarian both use
them verbatim.

`description` and `summary` are **not the same field and are not
interchangeable**: `description` is the stock base field — one sentence,
consumed by `regen-index.py` (it's what prints next to the page's wikilink
in `index.md`) and by agent scans. `summary` is a health-type-specific field
— the one-line statement/summary the librarian and later tooling read as the
domain content. Every health page needs both; don't conflate them or drop
one because the other looks redundant.

**`Study`** (`studies/`):
`summary`, `doi`, `year`, `design` (`rct | cohort | case-control |
cross-sectional | animal | in-vitro | review | meta-analysis`), `n`,
`population` (`pct_female`, `age_range`, `conditions`), `sex_stratified`
(`yes | no`), `evidence_gap` (omit, or `women`), `funding` (`public |
industry | mixed | not-reported`), `tier` (`narrative | structured`). Body
opens with a `⚠️ Evidence gap — women` callout when `evidence_gap` is set,
then `## Summary`, `## Key findings`, `## Limitations`, `## Links`.

`population.conditions` holds **short plain labels** for the studied
cohort (e.g. `pcos`, `healthy`) — it is not a list of `[[conditions/...]]`
wikilinks and isn't rendered as one; frontmatter values stay plain text.
When a label has a matching `conditions/` page, link it from the page
**body** instead (e.g. in `## Links`, `Studied population: [[conditions/
pcos]]`) — that's where the wikilink belongs, not in the frontmatter field.

`tier` sets how deep the extraction goes for this study: **`narrative`**
means the study gets a page here only — `## Summary`/`## Key findings`/
`## Limitations` — and no claims are extracted from it yet. **`structured`**
means the study page *plus* one or more `claims/` pages extracted from it
(via `supports`). `.kdb/kit.json`'s `default_tier` sets which tier new
studies start at when not otherwise specified (the kit repo's
`config/kit.json` is only the shipped default; `bootstrap.sh` copies it to
`.kdb/kit.json` on first install, and that vault-relative path is what the
librarian reads and what the owner edits afterward); either can be promoted
from `narrative` to `structured` later by adding claim pages.

**`Claim`** (`claims/`):
`summary`, `statement` (one precise, falsifiable sentence), `grade` (`A |
B | C | D` — see rubric below), `applies_to` (populations, e.g.
`women-18-45`, `postmenopausal`), `sex_note`, `evidence_gap` (omit, or
`women` — inherited from any supporting study that carries it), `supports`
(`studies/...` page names), `contradicts` (`studies/...` page names, or
empty). Body: `## Basis` (grade rationale), `## Notes`.

**`Intervention`** (`interventions/`):
`summary`. Body: `## What it is`, `## Evidence by population` (one
subsection per population, citing `claims/...` pages, gaps stated
explicitly), `## Open questions`, `## Safety flags` (**mandatory** —
pregnancy/trying to conceive, eating-disorder history, diabetes/medication
interactions, underweight, adolescents … whichever apply), and the
not-medical-advice caveat (§8).

**`Condition`** (`conditions/`) and **`Topic`** (`topics/`):
`summary`. Body: `## Overview`, `## Relevant claims & interventions`
(wikilink list).

## 4. Evidence-grade rubric

Every `Claim` carries a `grade`:

- **A** — ≥2 concordant human RCTs, or a meta-analysis, with adequate N.
- **B** — 1 RCT, or strong cohort evidence.
- **C** — observational, small-N, or conflicting evidence.
- **D** — animal, in-vitro, or expert opinion only.

**Population adjustment:** a claim's grade drops one letter *for the
population named in `applies_to`* whenever the supporting evidence carries
`evidence_gap: women` — the letter grade reflects strength of evidence for
that specific population, not evidence strength in general.

## 5. Women's-data-gap rule

When a study is male-only, or reports results that were never sex-stratified,
set `evidence_gap: women` in its frontmatter and add the ⚠️ body callout (one
line: which — male-only cohort, or not sex-stratified). Any `Claim` that
cites such a study as support **inherits** `evidence_gap: women` and states
in `sex_note` what is and isn't known about the sex-specific effect. The gap
propagates forward through `interventions/`/`conditions/`/`topics/` pages
that cite the claim — do not let it get silently dropped by summarization.

## 6. Write policy

Two-tier, same as stock kdb, plus one standing exception for this vault:

1. **`inbox/` is world-writable.** Anyone — any Claude session, the owner —
   may drop files there: clippings, extracted-claim drafts, session reports,
   one-line notes.
2. **Everything else is librarian-only for research content.** Only the
   `kdb-librarian` skill creates or updates `studies/`, `claims/`,
   `interventions/`, `conditions/`, `topics/`, and the stock types. A Claude
   session with knowledge to contribute writes a file into `inbox/` — it does
   NOT edit pages directly.
3. **Standing human exception — personal health pages.** The owner
   hand-authors her own personal health pages directly (outside the
   inbox → librarian pipeline). These pages are **read-only ground truth** to
   the librarian and to `lint.py`/`regen-index.py`: no rewrite, no
   re-schema, no normalization, unless the owner asks for it. Their folder
   structure and frontmatter schema are **co-designed between the owner and
   the assistant later**, once real content exists, and registered in
   `.kdb/types.json` at that point — this kit deliberately pre-creates
   nothing personal.
4. Raw entries (`studies/`) are immutable once ingested; analyses, grading,
   and product concepts are separate derived pages (`claims/`, topic notes,
   etc.) that link back to the raw page rather than editing it in place.

## 7. Privacy

Personal health data never leaves this Mac. It never goes into an email
draft, a chat reply meant for anyone but the owner, or any other outward
payload — this vault has no remote, by design, and that is deliberate, not
an oversight to work around. Treat any page under the owner's
hand-authored personal-health area (§6.3) as maximally sensitive by default
even before its schema is formalized.

Honest caveat on the above: "never leaves this Mac" means no outward
payload — no remote, no email, no upload. It does not mean invisible to
the local assistant. The SessionStart hook injects `index.md` (every
page's title and one-line `description`, personal pages included once
registered) into the context of every Claude Code session on this Mac at
startup, and any page the owner or assistant opens or discusses is read
into that session same as any other page. That reading happens locally, in
a session running on this Mac, and is never itself sent anywhere beyond
answering the owner's own question — but it is not invisible.

## 8. Safety caveat

> This library informs product design. It is **not medical advice**;
> consumer-facing claims need their own regulatory/clinical review.

This caveat appears on every `Intervention` page and applies to the vault as
a whole: grading and synthesis here are research judgments, not clinical
guidance, and nothing in this vault should be surfaced to an end user as a
medical recommendation without that separate review.

## Commit discipline

Every librarian operation ends with a **local** git commit in this repo —
this vault has no remote (§7), so there is no pull or push, ever. A failed
commit is noted in `log.md` and retried next operation — it never blocks the
operation itself.
